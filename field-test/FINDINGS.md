# FINDINGS — the field-test deep review

> **Status:** draft findings, 2026-11-25. **No fixes applied.** This document reviews what
> the field test has produced so far; the artifacts, schemas, RACI, and plans are unchanged.
>
> **Scope reality check:** **all four are now run** — [`01-kubernetes`](01-kubernetes/),
> [`02-grafana`](02-grafana/), [`03-deno`](03-deno/), [`04-rust`](04-rust/). Conclusions rest on
> **n = 4**, but the **method caveat** below still applies (single-context generation).

---

## 1. What the field test is, and how it was reviewed

The field test (plan item **X2**) runs real open-source features through the kit's loop —
PMT → TPM → SDM → SDE — and scores the artifacts against the project's own shipped design.

**Feature run (01):** Kubernetes **KEP-1287 — In-place Update of Pod Resources** (`stable`;
alpha v1.27 → beta v1.33 → stable v1.35). Six artifacts were generated and compared to the KEP.

**How this review was done:** every artifact was checked **against its bound output schema**
(the template in `shared/output-schemas/`) and **against `shared/raci.md`** (decision rights).
That is the review the first generation skipped.

### Method caveat (read this before trusting the numbers)

The artifacts were generated by **one agent in one context**, following the kit's skills and
schemas — **not by four separate single-role sessions**. So this run tests the *schemas and the
instructions' clarity*, but it does **not** test role isolation, the relay hand-off, or a
fresh-session load. Those are untested here.

---

## 2. What worked

1. **The `[CONFIRM]` discipline held under a large, complex feature.** No roster, PTO,
   estimates, or slack were invented; every missing input came back as `[CONFIRM]`. The kit's
   central promise survived contact with real material.
2. **Schema binding mostly took on the first pass.** 3 of 6 artifacts were **fully**
   conformant (stories, sprint plan, test plan); the rest had **detail-level** gaps — a missing
   story block, an empty cell, an over-reaching row — all enumerated in §7.2. None invented data
   to fill a gap.
3. **The problem chain reproduced the feature's shape.** Problem → goals → non-goals →
   requirements → edge cases (EC-1…9) mapped cleanly onto the KEP's Motivation/Goals/Non-Goals.
4. **The SDE half is strong.** The design's four resource states, `/resize` subresource,
   failure modes with detection, and rollback traced to the KEP; the test plan hit all five
   layers (Unit · Integration · Contract/API · E2E · Non-functional) including negative paths.
5. **Cross-domain fit.** A Kubernetes *infrastructure* KEP produced usable PMT/TPM/SDM/SDE
   artifacts — the kit is not tuned to one feature type.
6. **The relay was followable.** IDs, milestones, and dependencies were consistent enough to
   trace the feature across four roles without contradiction.

## 3. What didn't work

### 3a. Template conformance

| ID | Issue | Severity |
|---|---|---|
| **T-1** | `sde-design` broke a schema rule — `technical-design-doc.md` requires *"file paths and symbols"*; the artifact named **components only** (`kube-apiserver`, `kubelet`) | Medium |
| **T-2** | The **TPM roadmap has no dedicated schema** — it only "follows the PRD table standards." It is the weakest-bound artifact and the only run skill without one of the five schemas | Medium |
| **T-3** | **`sde-design` (01) left FM-5's Detection cell as `—`** — the schema says *"failure modes without detection paths are incomplete rows"* (found in the second pass, §7.2) | Medium |
| **T-4** | **`pmt-prd` (01) journey rows 2–3 carry `—` in the User action column** — a step with no user action is a system note, not a journey (§7.2) | Low |
| **T-5** | **`pmt-stories` (02) holds an `Epic`-typed row in the stories table** — breaks the schema and the CSV-import shape (§7.2) | Medium |

### 3b. RACI / ownership (the most serious findings)

| ID | Issue | Severity |
|---|---|---|
| **R-1** | **Milestone data asserted by two A/R owners.** The PRD's "Rollout" carried v1.27 → v1.33 → v1.35; the matrix assigns *"Program roadmap & milestone sequence"* to **TPM A/R** (PMT is only C) | High |
| **R-2** | **An engineering metric on the PMT row.** *"Success metrics & guardrails"* is PMT A/R, but the PRD's metric was `kubelet_pod_resize_duration_seconds` — an SDE concern, duplicated in `sde-design`. The **product outcome** metric was missing | Medium |
| **R-3** | **Dependency IDs collided across owners.** Stories used **DEP-1…4**, the roadmap **DEP-1…5** — same prefix, different referents. *"Cross-team dependency commitments"* is **TPM A/R** | High |
| **R-4** | **No traceability.** Nothing mapped **REQ-n → US-n → T-n**; a reviewer cannot follow a requirement to its story to its task | Medium |

### 3c. Cross-artifact consistency

- **Duplication.** For a design-led (infra) feature the PRD and the SDE design were
  **near-redundant** — a KEP *is* a design doc, so the PRD restated it. Milestones and metrics
  each appeared in two artifacts.
- **The relay wasn't demonstrated.** The **Handoff Block** (kit item W7) was never emitted, so
  the "carry the artifact forward" mechanic went untested.
- **A schema-shaped artifact can still be wrong.** The generation was fluent; the **review** is
  what caught R-1…R-4. That is the kit's own thesis, proven on itself.

### 3d. Method / test validity

- **Single-context generation** → role isolation, the relay, and the load order are untested.
- **Now n = 4** — all four repos are run. **T-1, T-2, R-4 recur in all four** (systemic);
  **R-1 in three** (not 02); **R-2 and R-3 in one** (01 only) — see §7.4. The recurrence is the
  strongest signal in the test.
- **The answer key can leak into the input.** For an infra feature, using the design doc's
  *Motivation* as "the raw problem" is close to using the design itself. The originating
  **issue/discussion** would be a cleaner input.

## 4. What needs to change

Prioritized. **Nothing here is applied yet** — this is the recommendation list.

### A. Kit / schema (candidate 0.2.0)

1. **A "design-led feature" mode** — start at SDE; make the PRD optional for features that are
   themselves design docs. *Fixes the PRD/design duplication.*
2. **A sixth schema: the program roadmap** (milestones + dependency table + critical path).
   *Fixes T-2.*
3. **A first-class milestone/rollout field, owned by TPM**, that the PRD *references*.
   *Fixes R-1.*
4. **A dependency-ID namespace rule** — the TPM owns `DEP-n`; downstream artifacts reference it.
   *Fixes R-3.*
5. **A metric split** — the PRD carries the **product outcome**; the design carries the
   **engineering** metric. *Fixes R-2.*
6. **A traceability convention** — `REQ-n → US-n → T-n`, carried across the relay. *Fixes R-4.*
7. **Enforce the design's "cite paths/symbols or `[CONFIRM]`" rule** (it exists; it was not met).
   *Fixes T-1.*
8. **A decision record (ADR) artifact** — the Deno run showed a **decision-only input has no
   home**; today a decision survives only as prose inside the roadmap's risk table.

### B. RACI / relay

9. **Emit the Handoff Block** so cross-owner data (milestones, deps) is *referenced*, not
   re-asserted — the mechanical fix for R-1 and R-3.
10. **Document the cross-team path.** The relay assumes one squad; a multi-SIG feature needs a
    rule — TPM owns the cross-team roadmap, and the SDM sprint plan is scoped to one squad or
    explicitly `N/A`.
11. **Make it a *mode*, not a rewrite.** The Grafana run showed the one-squad assumption is
    **right** for single-team features and wrong for cross-team ones (Kubernetes, Deno) — so the
    relay needs a **cross-team mode**, not a redesign.

### C. Method (for the field test itself)

12. **Run each role in a separate session** (fresh context) so isolation and the relay are
    actually tested.
13. **Use the originating issue/discussion as input**, not the design doc's Motivation.
14. **Record input quality + leakage risk per run** — a design-rich KEP vs a decision-only
    issue vs a conversation-decided API are not comparable without it.

---

## 5. Open questions

- Is the PRD/design duplication a **schema** problem, or a **wrong-feature-type** problem (infra
  KEPs are designs, not products)?
- Should the roadmap become its **own schema**, or a **section** of the PRD schema?
- Does a "design-led" mode break the RACI (PMT becomes I on an artifact it used to own)?

---

## 6. Verdict

**The kit works on real work — across four runs, with caveats.** Its honesty discipline is real
and its artifacts are mostly schema-conformant. The deep review found **template issues
(T-1…T-5) and RACI violations (R-1…R-4)**; the second pass (§7) corrected the recurrence
claims — **T-1, T-2, R-4 are systemic (all four repos)**; **R-1 in three** (not 02); **R-2 and
R-3 in one** (01 only). Every one is a **0.2.0 candidate**, not a correctness failure.

The most important lesson is methodological, twice over: **a schema-shaped artifact can still
violate the RACI and collide IDs — the review is the product.** And the review itself needed a
second pass: the first findings overgeneralized ("recurred in all four") and missed two
incomplete story blocks and a rule-violating failure-mode row. The field test should still be
hardened (separate sessions, cleaner inputs) before its results are quoted.

### 7.3 Quality of the artifacts

**Strong:** every PRD carries sourced numbers and real edge-case tables; the stories that exist
are vertical slices with Given/When/Then ACs; the test matrices hit all five layers with
negative paths; the designs show real flows and rollback steps. The `[CONFIRM]` discipline held
everywhere team data was absent.

**Weak:**
- **The SDM artifact is contentless in all four runs** (every cell `[CONFIRM]`) — the SDM hop
  was never substantively exercised, only its refusal-to-invent behavior.
- **02's design is the kit's own inference** dressed as a design (correctly labeled, but thin).
- **03's PRD bakes the held-back resolution into its Goals** ("align with the Node API") — that
  decision was the answer key; the input mentions Node as prior art, so it is *inferable*, but
  the run records no distinction between inferred and decided. **Answer-key leakage risk.**
- **Journey/step quality** (T-4) and **incomplete rows** (T-3) show fluent generation skipping
  schema details.

### 7.6 What worked well

1. **`[CONFIRM]` discipline, four for four** — no invented rosters, dates, metrics, or owners
   anywhere; the kit's core promise held on every run.
2. **Schema binding mostly took on first generation** — the PRD/stories/sprint/tests shapes
   were right without re-prompting; the failures were detail-level (a cell, a block, a row).
3. **Four domains, one kit** — infra KEP, UI feature, runtime API, language RFC all produced
   usable artifacts; no feature-type tuning.
4. **Honest thin-input handling** — 02 flagged its problem as *inferred*; 03's roadmap caught
   "the decision was the work"; neither dressed inference up as sourced fact.
5. **Recurrence analysis worked** — running all four turned one-off issues (T-1/T-2/R-4) into
   systemic signals, and cleared two false alarms (R-2, R-3).
6. **The review itself proved the thesis** — a fluent, schema-shaped output still needed a
   reviewer's pass, and then the reviewer's pass needed one too.
